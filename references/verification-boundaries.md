# Verification Boundaries

A successful command is sufficient evidence for the operation its contract promises. Additional verification needs a concrete, consequential failure mode that success does not cover; generic reassurance is not enough.

- Before adding a check, identify the uncovered property, the consequence of getting it wrong, and why existing checks or command outputs cannot establish it. Keep this judgment internal unless the tradeoff needs discussion; do not produce a justification checklist.
- Keep checks that establish distinct contracts: source tests, artifact compatibility, and publication are different operations. A successful build does not prove installed behavior, and a successful dry run does not prove publication. Reuse existing evidence until relevant inputs change.
- Let the owning command or composite action handle completion checks, retries, and propagation waits. Do not append duplicate registry lookups, tag polling, fixed sleeps, or custom verification scripts to successful publishers. If a shared action lacks a necessary guarantee, fix its contract rather than recreating it in each consumer.
- Distinguish completed work from accepted or queued work. When completion is required, use the command's supported wait or the operation's terminal status; acceptance alone is sufficient only for a submission request.
- Add a separate post-success check only for an explicit user request, an uncovered acceptance criterion, a known defect, or a consequential boundary such as silently dropped fields or partial multi-step mutations. Retain those readbacks inside their owning integration; callers should not repeat them after verified success.
- When external visibility itself must be checked, allow for documented propagation delays, use bounded polling, and report unresolved visibility separately from publication failure. Never republish merely because a cached lookup has not caught up.
- Report what the evidence establishes. Successful publication need not establish downstream installation or runtime activation unless that is part of the requested outcome.

## Validation Selection

- Run inexpensive baseline checks routinely for implementation changes, then select lint, type checks, builds, and component tests from the changed behavior and affected consumers. Include relevant callers and runtime adapters; matching changed filenames alone does not establish coverage. Documentation-only changes need applicable checks, not automatic behavioral suites.
- Prefer focused local checks. Broaden to a full local suite only when a named unresolved risk cannot be covered reliably by focused checks, impact cannot be bounded, failures reveal wider consequences, or the operator explicitly requests it. A push or handoff alone is not a reason to run the full suite.
- Preserve required coverage at its designated CI or release gate and honor explicit repository requirements. When a repository unconditionally requires expensive local validation, propose a scoped policy change rather than silently skipping the requirement. Retain conditional artifact, platform, and release checks for their distinct contracts.
- Reuse passing results until relevant source, configuration, dependencies, fixtures, or build inputs change. Prepare artifacts required by selected tests without repeating unchanged setup unnecessarily. Explicit test selection must not silently expand to the whole suite or report success when no tests matched.
- Report focused local results separately from full-suite and hosted results; queued or unrun checks are not passes. Measure local feedback time separately from CI execution, runner cost, and start delay. Duration informs selection and test-design review, not automatic exemption or removal.

## Evidence and Static Checks

- Classify each assertion by what it establishes, even when one suite mixes evidence. Use the [shared testing layers](./coding-stack-preferences.md#testing-defaults) for behavioral coverage. A runner name does not turn static inspection into a unit test.
- Static checks inspect source or artifacts without executing the behavior they describe. Retain one only for a named correctness, compatibility, safety, or maintenance invariant with a concrete failure consequence that existing validation does not cover. Prefer existing syntax, schema, lint, or build checks to new snapshots of configuration or implementation layout.
- Justified: parse a workflow and verify its token permissions stay restricted, preventing credential exposure; validate that a package export resolves inside the packed payload, preventing a broken consumer entrypoint. These establish configuration or packaging invariants, not successful execution of a workflow or installed import.
- Unjustified: snapshot an entire workflow to freeze YAML ordering, compare complete documentation paragraphs, or count helper calls merely to preserve today's implementation. Remove redundant assertions rather than relocating them into another suite.
- Reading fixture files while executing the production parser is behavioral coverage. Classify its boundary under the shared model; reading files alone does not make it static inspection.
- Preserve distinct safety, protocol, and packaging checks where exact details are contractual. Retained static checks may share an existing command with behavioral tests; no fourth suite is required. Report their evidence separately from runtime proof.

## Assertion Strength

- The agreed product contract is authoritative. Tests are its executable specification and may themselves be wrong; reconcile a conflicting expectation instead of treating a passing suite as the definition of desired behavior.
- Apply the same admission and retention gate: a test must reject a plausible, consequential error in owned behavior, provide worthwhile evidence beyond existing checks, and earn its fixture and maintenance cost at the smallest faithful boundary. Be able to name the wrong decision or effect and explain why the assertion would reject it. Uniqueness, speed, a new helper or file, “adds coverage,” and just-in-case reasoning are insufficient. No mandatory mutation tooling or per-test paperwork is needed.
- Compare evidence across layers before adding or retaining tests. Removal can follow retained worthwhile coverage, an obsolete requirement, or a deliberate decision to leave low-consequence detail untested because its cost exceeds its protection. A unique test need not be replaced or relocated; no deletion target or coverage percentage applies. Classify assertions by contract and boundary, not filename, implementation language, runner, or duration; mixed specs may need several owners' criteria.
- Preserve meaningful authorization, identity, destination, resource, duplicate-effect, and uncertain-effect protections during consolidation. A test calling a restriction a safety guard does not establish that the product requires it; trace the agreed requirement and actual consequence.
- Judge an assertion by the regression it detects. Derive expected results from the supported contract or a known input/output example, not by repeating the implementation's calculation or copying its current output.
- Reject by default incidental prose, source, layout, count, or invocation freezes; internal choreography; tests replaying their own mocks; third-party behavior; and permutations without distinct meaningful failures. Exact assertions remain appropriate for consequential owned rendering, schema, protocol, configuration, artifact, and safety contracts. Effect/no-effect assertions, including calls that establish an external effect, remain valid; mocking an external boundary alone does not make a test low value.
- For structured data, use an existing parser or validator and assert meaningful fields and relationships. Preserve checks for permissions, credential isolation, artifact selection, and required-check identities; formatting changes alone should not break them. Do not build a bespoke parser to police incidental syntax.
- Before removing or loosening a check, identify its actual protection and apply the retention gate. Preserve meaningful critical protections, not every unique assertion. A test becoming inconvenient after a change is not evidence that it is unnecessary; quantify or explain fixture coupling and maintenance burden against the consequence it prevents.
- When supported runtime adapters promise shared configuration semantics, exercise those semantics through each adapter, not only the shared parser. Cover omitted and explicit values, invalid input, and unavailable configuration with focused cases; distinguish an absent optional source from a selected source that cannot be read rather than silently treating both as defaults. Derive expectations from the promised contract, preserve documented runtime differences, and use the existing suite without an automatic OS/runtime cross-product.
